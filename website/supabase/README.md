# Post-event badge collection: live upload contract

`/sync` reads the existing USB `snapshot` command when the user clicks
**Sync badge data**, then POSTs the snapshot to the `badge-relay` Supabase
project (`https://qoouxoeavyuokuscvxff.supabase.co`, the same project behind
`tools/relay_server`). The page explains that badge data is uploaded to Hack the
North. It waits for a successful upload before offering **Unlock all apps**.
Unlocking uses that original backup and upload, verifies only the launcher
settings, and never takes or uploads another snapshot. The separate identity
workflow uses USB only; it does not take a snapshot or upload to Supabase.
Upload failures are visible; the user can retry without another USB read or write.
Requests time out after 30 seconds. No login or badge token is required.

The latest snapshot, read time, source, and recovery backups are saved in
browser local storage and restored on return. Storage failures do not block
sync or downloads. Restoring or downloading a snapshot never uploads it, and
restored data cannot skip the connect/sync steps for a new session.

The snapshot is the firmware's v1 `fs_mirror` document, unchanged. It includes
text files, unknown app data, counts, and completeness markers. Binary files
are represented by skip records; oversized files can be truncated or skipped,
and heap pressure can omit files. This is the same export as the serial sync,
not a byte-for-byte disk image. Partial snapshots are handled silently; their
original completeness markers remain in JSON and file details.

## Schema

The table lives in the shared project, applied with the other migrations
(see [`tools/relay_server/supabase/migrations/20260920000000_badge_dumps.sql`](../../tools/relay_server/supabase/migrations/20260920000000_badge_dumps.sql)).
(There is no standalone SQL file in this folder; the migration is the single
source of truth and ships with `supabase db push` from `tools/relay_server`.)

Each submitted snapshot produces one immutable row:

| Column | Generated by | Meaning |
| --- | --- | --- |
| `dump_id` | Postgres UUID default | Unique dump ID, even for simultaneous uploads |
| `dumped_at` | Postgres `clock_timestamp()` | Automatic server timestamp with timezone |
| `dump` | Badge / browser | The complete JSON document received from the badge |

A separate UUID avoids timestamp collisions while retaining the automatic
server timestamp requested for each dump. Clients may insert only `dump`, so
cannot choose their receipt time or ID. Repeated submissions create new rows;
nothing overwrites an earlier snapshot. The JSON badge ID can be queried by
organizers later without a separate identity service.

Access is append-only: RLS is on, the browser role has `INSERT (dump)` only,
and there are no SELECT, UPDATE, or DELETE grants or policies for `anon` or
`authenticated`. Read access is only for organizers through Supabase's
dashboard or a server-side key. The firmware snapshot can include the Solana
wallet's private backup and contact details, so keep public reads disabled
and choose retention deliberately. Anonymous submissions are unverified data,
not authenticated proof of badge ownership or scores. For a public collection
endpoint, add request size and rate limits at an Edge Function/proxy if abuse
becomes a concern; do not solve this by putting a privileged key in the page.

## Setup

1. From `tools/relay_server`, link and push (DB password reset under
   Database Settings if needed):
   `supabase link --project-ref qoouxoeavyuokuscvxff && supabase db push`.
   This applies `badge_dumps` alongside the relay tables, including the
   anonymous-insert policy.
2. The **publishable key** (`sb_publishable_...` from the project's Connect
   dialog / Settings → API Keys) is hardcoded as the default in
   `src/sync/supabase.js`, so uploads work with no further setup. Never use
   the database password, secret key, or `service_role` key in browser
   configuration.
3. Only to override: set `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` in
   Netlify (Site settings → Environment variables) and redeploy, or in
   `website/.env` locally (see `.env.example`). An explicitly blank
   `VITE_SUPABASE_ANON_KEY` disables uploads.

## Browser upload contract

`src/sync/supabase.js` (`uploadSnapshot`, covered by
`tests/sync-supabase.test.js`) sends the append-only request:

```http
POST <PROJECT_URL>/rest/v1/badge_dumps
apikey: <PUBLISHABLE_KEY>
Content-Type: application/json
Prefer: return=minimal

{"dump": <the original fs_mirror object>}
```

Expect HTTP 201 with an empty body. There is no attendee login, secure badge
code, upload token, or returned profile write. Use the publishable key in the
`apikey` header; do not treat a modern publishable key as a Bearer [REDACTED] No SDK
is required. The schema permits partial snapshots so data can still be
collected; use their `complete`, `counts`, and file markers during analysis.

Each explicit sync produces a new row. Unlock and identity edits do not upload
again, and the before-identity-edit backup stays local. An upload failure keeps the received snapshot and USB
connection, shows an error, and offers Retry sync without repeating the write.

Official references: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security),
[API keys](https://supabase.com/docs/guides/getting-started/api-keys),
[tables and defaults](https://supabase.com/docs/guides/database/tables).

## Release badge writes

- Local Vite development: enabled, so a connected badge can be used to test.
- Other production builds: disabled unless explicitly enabled.
- Netlify enables `VITE_POST_EVENT_UNLOCK=true` and
  `VITE_POST_EVENT_IDENTITY=true` in the repository's `netlify.toml`.
  To test the production flag locally: `VITE_POST_EVENT_UNLOCK=true npm run build`.
- Identity writes have a separate `VITE_POST_EVENT_IDENTITY=true` flag. If
  disabled, the identity form is visible but its Upload button is disabled.
  Local Vite development enables both actions for testing.

The UI and serial methods both check these build-time switches; changing the
disabled button alone cannot trigger a write. They are release gates, not a
firmware security boundary. Existing firmware already permits token-free USB
file writes, including through other serial clients. No admin password is
embedded or sent. Unlock keeps the synced snapshot downloadable, checks the
current launcher settings, and appends the known public app slugs to the complete
`config/system.cfg` while preserving other lines and existing launcher order,
writes with paced 128-byte chunks, verifies the file, restarts, and verifies
all public slugs in the launcher settings. Internal apps are not added. No firmware
build/flash or admin password is required. Avoid pressing badge buttons during
the write; keep USB connected. A failed operation disconnects instead of
sending another command into a potentially unfinished transfer. The downloaded
before-unlock JSON retains the original launcher settings for recovery.

Identity saving reads `prov show` and `identity.json` directly, validates firmware
field capacities and contact formats, and checks that a fresh read still matches
the identity being edited. A missing file is allowed only on an unprovisioned
badge, so registration works even if snapshot/server sync cannot. The editor
preserves unknown fields and registration metadata, writes only
`/littlefs/identity.json`, checks exact readback, calls `prov apply`, and verifies
the loaded ID and file. No reboot or token commands are used. Existing firmware
replays the registration tutorial when `prov apply` succeeds. Changing the badge
ID changes future connections and can invalidate an old event token bound to it.

USB `put` writes directly to the destination file and is not atomic. An
interruption can leave a partial file. The original event snapshot remains
available for download; identity edits try to persist the previous raw identity
separately under `htn-badge:identity-backup:v1` in local storage before writing.
Automatic rollback is not implemented. A snapshot can omit binary/truncated
files and is not a firmware backup.

The separate **Reset your badge** dropdown matches the dashboard reset. Only
after the owner explicitly acknowledges deletion and clicks the reset button,
it sends `prov erase confirm` to remove identity, registration, and the on-badge
sync credential. After verifying that receipt, it sends `factory_reset confirm`
to clear `/littlefs/config`, `/littlefs/apps`, and `/littlefs/appdata` and restart.
Solana wallet keys and server backups remain. Reset does not upload data;
partial failures explicitly report when identity has already been erased.
Success requires the reset receipt, not a new console prompt after reboot.
The USB port is then released; reconnect and register the badge again.

The “Official firmware” panel flashes the committed image set in
`public/firmware/` (the same bytes `rapid-flash` flashes) in-browser over
Web Serial via the vendored esptool-js bundle, with a manual esptool command
under Advanced for fallback. See
[`public/firmware/README.md`](../public/firmware/README.md) for refresh steps.
